# Aegis Browser 0.6 — appearance and test report

22 October 2026. Android Next 0.6.0; desktop benchmark uses the existing 0.5.1 desktop shell. This report does not establish a fastest-browser or best-ad-blocker ranking.

## Mobile appearance delivered

Menu → Appearance → Theme offers Follow system, Light and Dark. The same menu offers Standard or Refined surfaces and Mint, Blue or Violet accents. Appearance preferences are shared by regular WebView and private/add-on Gecko views. Refined styling uses rounded address cards, depth, coordinated controls and the local new-tab background; Standard uses simpler surfaces. These are appearance choices, with no paid tier.

Changes apply to existing views rather than recreating the activity, clearing storage or reloading tabs. uiMode changes are handled for Follow system. The browser controls and local new-tab page are themed; website content controls its own colours. Menu dialogs follow the chosen light/dark activity theme.

## What was checked

- Release APK compilation and lint; zero lint errors. Existing warnings concern the target SDK, JavaScript and English UI text.
- ThemePaletteTest: 36 combinations of theme/style/accent/system preference; 288 text-on-surface/background contrast checks at a minimum 4.5:1, including muted and private indicator colours. Invalid preferences safely fall back to supported settings.
- New-tab HTML was rendered at a 390 × 844 viewport with CSS generated by the compiled Java appearance helper. Light/Dark × Standard/Refined checked: correct scheme, wallpaper mode, usable search field and no document-width overflow. The four internal captures were inspected; they are not Android native-widget screenshots.
- Domain matcher boundaries, final-dot hostnames, the narrow advertising-path supplement, query safety, malformed URLs and null hosts passed. Popup Open/dismiss/cancel decisions still complete exactly once. HTTPS/credential/private-extension navigation guards passed.
- No Android phone/emulator is attached. Native settings dialogs, live Follow system transitions, native widget rendering, preserved live sessions and live MSN/YouTube flows still need device verification. Theme persistence is implemented with shared preferences; its native UI lifecycle is not certified by the palette tests.

## Controlled desktop page-load lab

The actual Aegis desktop application loaded two local article fixtures. Each condition has seven measured runs, preceded by warm-up, with paired/alternating protection-on/site-paused order. HTTP cache was cleared before every measured load and resources used no-store. Both conditions used the same Electron renderer, application and hardware. All test origins resolved to loopback. The article's text and legitimate API response remained present.

The ad-heavy fixture deliberately contains 12 synthetic ad scripts on a known ad hostname. Each carries approximately 64 KiB, an artificial 80 ms server delay and 6 ms of renderer CPU work. This intentionally demonstrates the work avoided by filtering; it is not a representative real-website sample.

| Fixture | Protection | Median end-to-end load | Median load event | Server body bytes | Ad requests reaching server | Rule blocks |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| clean | on | 40.5 ms | 26.9 ms | 134,174 B | 0 | 0 |
| clean | paused | 40.9 ms | 27.4 ms | 134,194 B | 0 | 0 |
| ad-heavy | on | 42.3 ms | 28.5 ms | 135,487 B | 0 | 12 |
| ad-heavy | paused | 220.2 ms | 216.9 ms | 923,439 B | 12 | 0 |

End-to-end time is navigation invocation through load completion and the legitimate API-ready check. Load event is the Navigation Timing loadEventEnd value. Body bytes exclude headers, TLS and protocol overhead. The clean fixture's small difference is not a demonstrated general speed improvement. The ad-heavy fixture benefited from avoiding the constructed ad payload; it does not predict a similar improvement for MSN, YouTube or other pages.

Host: linux x64, AMD EPYC 9V74 80-Core Processor; Electron 45.0.0, Chromium 156.0.8078.48. Root/headless test harnesses bypass the OS sandbox only for CI; distributed application sandbox settings were retained. Tests exclude cold app startup, battery, real-network latency, GPU/video performance and memory comparisons.

## Android request filtering: small curated corpus

The bundled list contains **93,731 domains**. The initial corpus result was 11/12 known advertising URLs blocked. It missed `adservice.google.com/adsid/…`; a narrow host-and-path supplement now covers this endpoint without blocking other Google services or other paths on that host. It remains active after host-list updates because it is part of the matcher.

After the fix: **12/12 known ad endpoints blocked; 0/12 ordinary controls blocked**. Controls include MSN article/image URLs, Wikipedia, GitHub, a font host, public CDNs and a query-string/boundary case. The final-dot hostname bypass is also corrected.

Both deliberate limitations still pass through: an advertising resource served from an otherwise normal first-party host, and an unlisted sponsor hostname. Therefore these results explicitly do not establish 100% ad coverage, absence of false positives on other sites, or live YouTube ad removal. The corpus is small and selected, not an independent internet-wide evaluation. URL classification was tested; real remote URL availability/content was not fetched by this check.

## Request-path microbenchmark

The regular Android WebView interceptor now uses its parsed host and path instead of converting/reparsing the entire URL. In a Java 17+35-2724 server JVM microbenchmark (9 alternating batches × 240,000 lookups), median lookup time was **57.1 ns using prepared host/path strings**, versus **515.3 ns including an extra URI parse**.

This excludes Android Uri extraction, network activity, UI work and page rendering. It measures the matching hot path, not Android browser speed or a whole-app multiplier.

## Popup choices

The actual desktop WindowOpenHandler was exercised with deterministic native-dialog responses: Block produced zero new tabs; Open produced one tab and loaded the legitimate destination. Dialog decisions were simulated at the native API boundary; this was not a physical desktop click test. Android's retained 0.5.2 popup handling provides Open/Block for script-created requests and allows approved article windows; its Java one-shot decision tests pass, but Android native transports/dialogs still need a device check.

Blocking every popup would also prevent some requested article/login windows. Aegis allows the user to approve them; the report does not treat every permitted window as a failure.

## Comparison limits and other browsers

No installed Google Chrome, Brave or Firefox executable, physical phone or working Android emulator was available. **No cross-browser ranking was performed. Aegis is not proven faster than all browsers or the best at blocking every ad/popup.** The paired desktop test is protection-on versus protection-paused within Aegis.

Chrome and Firefox already provide mobile Light/Dark/device-theme choices; this release adds parity and Aegis styling, rather than an exclusive feature:

- [Google Chrome Android theme documentation](https://support.google.com/chrome/answer/9275525?co=GENIE.Platform%3DAndroid&hl=en)
- [Firefox Android theme documentation](https://support.mozilla.org/en-US/kb/using-dark-theme-firefox-android)

## Reproduction

The source archive contains `benchmarks/desktop-lab.cjs`, `benchmarks/popup-lab.cjs`, `benchmarks/FilterLab.java`, initial/final filtering JSON and all raw desktop runs. Desktop harnesses require the source's pinned Electron/node dependencies and Linux loopback/headless support. Run the Java filter lab with the APK's actual domains.txt, not a substitute list. These local harnesses are development tools; no benchmark server or artificial workload runs during normal browsing.
